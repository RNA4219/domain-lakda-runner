# 改修要件のレビュー用要約

## 1. 今回決める完成形

今回の仕上げは、テスト終了後にHTMLを開き、結果の概要・失敗理由・保存済みの画像や動画を確認できる状態に絞る。2026-09-11のユーザー指示により、比較・開発用テストの集約・レポート履歴管理は保留とする。基本機能の使いやすさと安定性を確認し、追加機能を完成条件にしない。

詳細の正本は[全体要件](20260910-detailed-requirements.md)、画面・入出力は[レポート詳細](20260910-report-detail.md)、確認方法は[受入チェックリスト](20260910-detailed-checklist.md)にある。本書は既存7改修・57要件（Must 55、Should 2）・22受入条件を読みやすくまとめたもので、新しい要件や承認を追加しない。実装状況は[仕様索引とTaskのEvidence](../spec/verification-reports/README.md)で確認する。

## 3. レポートの初期版

ここでの「ClaudeのArtifactのようなもの」は、結果を見ながら絞り込み・詳細選択・媒体閲覧ができる成果物を指す。生成と閲覧にClaudeのアカウントやAPI、AI処理を必須としない。

| 項目 | 要件案の既定値 |
|---|---|
| 対象 | Lakdaの5 mode、worker batch、探索session、明示指定した複数の保存結果 |
| 生成のタイミング | 対応CLIの終了後。明示offが可能。保存済み結果からも再生成できる |
| 成果物 | `index.html`と同梱assetsのフォルダ。ブラウザを手動で開き、フォルダを移動してもオフラインで操作できる |
| 表示言語 | 日本語（`ja`、既定）／英語（`en`）を出力時に選択する。見出し・説明・操作ラベルを切り替え、保存されたメッセージ・ID・コードは原文を保つ |
| 概要 | 実行結果、停止理由、日時、所要時間、対象・mode、run／session、seed、revision、未確認事項 |
| 一覧・詳細 | 状態・platform・mode・severity・キーワードで絞り込み、選択した項目のmessage・履歴・参照証跡を表示する |
| 画像・動画 | 保存済み媒体を閲覧する。項目との明示的な対応がなければ「実行全体の証跡」として表示する |
| 保存・共有 | 自動生成は`local`。`share`は検査条件と機密区分に従って媒体を含める。除外理由を表示し、自動アップロードしない |
| 再生成 | 元runと以前のレポートを保持し、新しい保存先へ出力する。入力を再実行・修復しない |

上記は提案上の既定値であり、ユーザーが個別に確定した条件とは扱わない。初期対象の「テスト」はLakdaの実行結果を指す。開発用の`npm test`／Pythonテスト結果を同じ画面へ集約する機能は、現時点では後続候補である。

## 4. 利用者が確認する受入シナリオ

次の数値は説明用の人工入力であり、実際の試験結果ではない。

| 操作・状況 | 合格とする動作 | 詳細AC |
|---|---|---|
| passed 1件・failed 1件を生成する | 確定run 2件と各結果が見える。生成が正常ならレポート状態はreadyで、元テストのfailedを維持する | AC-UP-012、014 |
| failedだけに絞り、1件を開く | 詳細と保存済み操作履歴へ辿れ、解除すると元の一覧へ戻る。総数と表示件数を区別する | AC-UP-014、015、020 |
| 画像がない、または表示条件を満たさない | 保存済み根拠に従って未取得・保持対象外・除外・対応未確認などを説明する。別画像を割り当てない | AC-UP-015、018 |
| 有効な開始記録だけが残る | localでは「結果未確定」として最小診断を出す。合否や操作数を推定せず、生成状態はdegradedとする | AC-UP-017 |
| テスト終了後にレポート保存が失敗する | 元テストのstdoutと終了codeを保ち、生成失敗を別通知する。未完成HTMLを完成品として出さない | AC-UP-012、013 |
| フォルダを移動し、ネット接続を切って開く | 絞り込み・詳細・同梱媒体を利用でき、外部通信が発生しない | AC-UP-019 |

## 5. 規模・操作性の目標

初期上限は展開後100 run、操作・event合計10,000件、failure・finding合計1,000件。上限超過を黙って切り捨てない。容量の上限は[レポート詳細8節](20260910-report-detail.md#8-非機能要件と数値の提案値)に従う。

基準環境で、無媒体レポートの生成10秒以内、最大件数で初期操作可能まで3秒以内、絞り込み更新p95が300ms以内を目標とする。WindowsのChrome／Edge、幅390pxを含む表示、100%／200% zoom、キーボード操作を確認する。これらは要件上の目標であり、実装の合格実績とは別に扱う。

## 6. 段階と残る判断

1. **M1：ローカルで結果を確認できる状態。** レポート、Python fixture検証、保守構造、現行手順を整える。通常Web結果の確認を実機準備待ちにしない。
2. **M2：実機と媒体の根拠を接続する段階。** 実観測、撮影の停止、媒体検査・署名の受渡しを統合する。
3. **M3：固定revisionでの受入。** 必要な実環境・実機・人間の確認と外部Gateを揃える。

前回比較・対話graph、AI要約、PDF／単一HTML／ZIP、開発用suite集約、レポート履歴管理は保留し、自動的に次の実装へ進めない。必要が生じた時点で改めて採用を決める。リアルタイム監視、レポートからの再実行、クラウド公開は初期範囲外とする。上記のM2・M3に残る実機連携・受入も、基本レポートを手元で確認するための追加機能にはしない。既存の未完了事項として記録を維持する。

要件レビューで変更する場合は、全体要件の既定値、対応する詳細要件、受入条件を一緒に更新する。チェックリストが未チェックであることと、個別の実装・ローカル検証が存在することは両立する。
