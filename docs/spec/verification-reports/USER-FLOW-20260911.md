# CLI実行からレポート確認までの利用フロー

既存の参照アプリをローカルで動かし、別processのCLIで通常runを実行した。正常終了・操作失敗・HTML自動生成・日本語／英語の再生成・画像と動画の確認を接続した。過去の保存runからの再生成・閲覧も確認した。

## 実行方法

`tests/report-user-flow.spec.ts`は既存の`docs/index.html`を127.0.0.1の動的portで配信し、`node dist/cli.js run --mode smoke --config <保存設定> --base-url <loopback URL> --report-dir <短い保存先>`を起動する。allowHostsは127.0.0.1だけ、単一worker、最大5操作、5秒、LLM不使用。serverは検査終了時に停止する。

| ケース | 実際の操作と結果 |
|---|---|
| 正常 | ページを開き「次へ」を2回押す。3操作完了、runはpassed、CLI exit 0。自動生成はready。保存方針に従い画像・動画は保持されない |
| 失敗確認 | 完了後に無効になった「次へ」をもう一度押す。4番目の操作が時間切れ、runはfailed、CLI exit 2、保存messageは`action timeout`。自動生成はready、画像・動画・traceを保持 |
| 日英再生成 | 保存されたaction sequenceのrun directoryから`report generate --report-language en`を実行。集計を保持し、英語の操作・画像表示と390pxの折返しを確認 |
| 旧run | 2026-08-02の保存runをそのまま入力。error／操作0件／手順0件を保持し、存在しない失敗手順への移動を表示しない。failure詳細から実行全体の画像・動画へ移動できる |

新しいテストの失敗は操作経路を確認するための意図した時間切れであり、参照アプリの新たな製品不具合として報告するものではない。過去runのmessageは`Error`、画像は白画面であり、それだけから当時の具体的な原因は確定できない。

## 見つかった不足と対応

**UF-01: 失敗手順を選ぶと、保存済み画像・動画へ辿りにくい。修正済み。** 通常runは画像・動画をrun全体として保持し、個々の手順への参照を持たない。そのため失敗手順へ移ると媒体0件の表示になり、履歴選択を解除するまで全体証跡を開けなかった。選択手順を維持したまま全体証跡を開くボタンと、手順との対応が未確認である説明を追加した。前／次で表示を戻し、動画を止め、再度開いたときの時刻を保持することを確認した。媒体を推定で手順へ割り当てていない。

**UF-02: Windowsの深い保存パスでは、画像を表示できない場合がある。保存先の制約として記録。** 検査用の自動生成先では画像の絶対パスが292文字になり、画像要素は存在したが`naturalWidth=0`だった。同一SHA-256のPNGを生成した183文字の保存先では読み込みが通った。verifyはどちらもvalidであり、表示要素の存在だけを調べるテストでは見逃す。テストを実画像decodeの確認へ強め、通常の保存階層に近い短いreport rootを使用した。ブラウザの長いパス対応自体は変更していない。

path比較は`.lakda/report-user-flow-path-comparison-20260911.json`。両PNGは45,062 bytes、SHA-256 `0a56d70e15e9e4a8d77d5be0e9920acd3e71773bbcd4e1eeb1e3fad669e6450b`。

## 確認記録

- doctorはconfig／Chromiumが利用可能。認証状態とLLMは未準備だが、今回の認証なしsmokeには不要。
- 先行する利用フローテストは正常ケース1件pass／失敗ケース1件fail。UF-01を検出した（`.lakda/report-user-flow-red-20260911.log`）。
- viewer・媒体の関連25件pass、22.8秒（`.lakda/report-user-flow-green-20260911.log`）。その保存画面の目視でUF-02を発見した。
- 実画像decodeを追加した検査は292文字の保存先でfail（`.lakda/report-user-flow-path-red-20260911.log`）。短い保存先で2件pass、動画再生・停止・位置保持を追加した段階でも2件pass、17.5秒（`.lakda/report-user-flow-final-20260911.log`）。
- 旧runの独立したoffline閲覧はpass（`.lakda/report-user-flow-old-ui-20260911/result.json`）。生成bundleは8 files／3媒体を保持し、verifyもvalid。
- 最終`npm run check`はdocs・型・lint・buildと全579件がpass、3.8分（`.lakda/report-user-flow-check-20260911.log`）。この実行には画像の原寸表示／縮小も含む利用フロー2件が含まれる。
- Chrome 152.0.7977.83／Edge 152.0.4191.66、1366×768／390×844、100%／200%の8条件40ケースがpass（`.lakda/report-user-flow-media-20260911/result.json`）。外部HTTP要求・page errorは0件。全体テストとの同時実行はしていない。
- offline `npm run pack:check`は595 files／65 schemasの構成検査と隔離install・CLI・report生成がpass。固定runtimeとの差による`EBADENGINE`警告は残る。

- 最終のCLIログ・入力run・画面は`.lakda/report-user-flow-verified-20260911/{passed,failed}/`へ保存した。画像原寸表示、録画の再生、英語390px、旧runの保存画面を目視し、失敗時の画面が`state: completed`で「次へ」が無効になっていることを確認した。
