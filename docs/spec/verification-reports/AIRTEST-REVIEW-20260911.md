# Airtestのレポートを基準にした見直し

この記録は改修前の評価である。AR-01〜03の対応と確認結果は[UI調整の記録](AIRTEST-ADJUSTMENT-20260911.md)を参照する。以下の不足点を修正した後も、Airtest実機との全機能・操作速度の同等性は未評価である。

基本的なHTMLレポートとしては使用できるが、失敗した操作と画面を続けて追う使い勝手は、まだAirtest相当とは評価できない。前回のUIR-01〜03は修正済みであり、その完了と今回の比較評価は区別する。

Airtestの基準は、公式ガイドと公開テンプレート・表示コードで確認した手順一覧、各手順の詳細、失敗手順への移動、成否／assertによる絞込み、画像サムネイルからの移動とする。[公式ガイド](https://airtest.doc.io.netease.com/en/IDEdocs/3.5about_report/Report_guidelines/)、[テンプレート](https://github.com/AirtestProject/Airtest/blob/master/airtest/report/log_template.html)、[表示コード](https://github.com/AirtestProject/Airtest/blob/master/airtest/report/js/report.js)。ガイドはIDE 1.2.12／Airtest 1.2.3を基にした文書であり、最新版AirtestIDEの全機能や実機での操作速度を比較したものではない。

| 観点 | 現在のLakdaの評価 |
|---|---|
| 結果概要・検索 | 合否集計、状態・重要度等の絞込み、メッセージ検索は使用可能 |
| 画像・動画 | 関連媒体の表示、画像拡大、動画再生、狭幅操作、日英出力は実装済み |
| 手順の理解 | 探索履歴は内部event名が中心で、操作・対象・判定を読み取りにくい |
| 失敗の調査 | 結果の絞込みはあるが、失敗手順へ直行し、前後の手順と画像を続けて確認する操作が不足 |
| 画面の主役 | 技術情報と媒体の説明が大きく、手順・判定・画面を並べて把握しにくい |

## AR-01 / P2: 探索履歴の説明と判定情報が薄い

`adaptive-history.ts:38`は通常の履歴labelをevent typeから作り、`run-history.ts:20`／`:41`はそのまま時刻なしの履歴へ投影する。現在の動画sampleは`operator-bookmark`と`oracle`が並び、runの失敗理由は`machine_failure`である。これだけでは操作対象や失敗した確認内容を読み取れない。

通常runの実行記録は`execution-history.ts:23`で操作kind・status・所要時間を文字列へ含めるので、全modeで情報がないという指摘ではない。ただし`ReportTimeline`には手順のstatus・duration・対象・判定内容の専用fieldがなく、viewerもlabel・種別・時刻の表示が中心である。

改善案: 保存済み記録から取り出せる操作名・対象の説明・判定結果・時間を手順単位で示す。取得できない内容は未取得とし、操作済みや成否を推測しない。元のID・message・eventは詳細に保持する。見た目のCSS調整だけでは解決しない。

## AR-02 / P2: 失敗手順と前後の証跡を連続して追いにくい

`viewer-client.ts:125`〜`:142`の履歴は100件ずつの一覧と証跡ボタンを持つ。選択した媒体からは「履歴の選択を解除」で元の手順へ戻れるが、失敗手順への移動、前／次の手順、手順の成否による絞込みはない。上部の絞込みはrun・failure・finding等の結果行を対象とし、手順の絞込みとは異なる。

改善案: 保存された失敗の対応先が特定できる場合に「失敗した手順へ」を表示し、選択中の手順・判定・対応画像を一か所で確認できるようにする。前／次の手順へ移る際も表示位置を保つ。サムネイル一覧は追加候補であり、最初の改修に必須とはしない。

## AR-03 / P2: 技術情報と説明が画像より目立つ

`viewer-client.ts:100`〜`:124`はID・seed・revision・実行資格等を媒体の前へ常時表示する。媒体カードも所属・未検査状態・理由を画像の前に並べる。PCの`selected-history.png`では、選択した履歴と説明に大きな面積を使い、画像は画面下端に一部だけ見えている。前回の移動ボタンは到達を短くしたが、画像中心の確認画面にはなっていない。

改善案: 手順名・判定・画像を先に置き、IDやrevisionは開閉する補足情報へまとめる。未検査・欠落の重要表示は簡潔に残し、対応する説明を参照できるようにする。PCは手順一覧と選択内容を並べ、狭幅では縦に配置する程度でよい。

## 確認範囲と次の基準

- 最終source／test／検査scriptの5 fileは前回保存hashと一致した。日英sampleのbundle verifyを再実行し、双方valid／7 filesを確認した。
- 生成JSON、描画コード、PCの履歴選択画面とmobileの詳細画面、前回の動画操作画面を照合した。保存画面は`.lakda/report-uir-media-verified-20260911/chrome-1366-1/selected-history.png`と`.lakda/report-uir-final-20260911/results/`配下。全入力は人工データである。
- 今回はsourceを変更せず、全571件と媒体40ケースは再実行していない。これらは[前回の検証](UI-REVIEW-FIXES-20260911.md)であり、Airtestとの使い勝手の同等性を検証した試験ではない。
- Airtestは公式文書と公開実装を参照した。公式画像は取得できず、Airtest画面の新たな手動操作や並列表示による比較は未実施。Lakdaも保存画面と生成物によるレビューである。

以下は提案する受入基準であり、まだ実装完了として扱わない。

- [x] AR-01: 保存内容に基づき「何を行い、どう判定されたか」を手順の見出しと詳細から理解できる。

次はこの3点に絞る。比較dashboard、レポート履歴管理、大規模なグラフ等の追加は不要。Airtestの全機能を複製することも今回の到達条件に含めない。
