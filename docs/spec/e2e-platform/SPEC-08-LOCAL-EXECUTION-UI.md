# SPEC-08　製品概要から開始するローカル実行

対象は FE-08 の Windows ローカル受入。既存の静的 HTML は保存記録の閲覧に使う。実行機能はループバックで起動した Lakda から提供する。[利用者要求](REQ-FRONTEND.md)

## 画面と状態

製品概要の「テストを実行」から登録スイートを選ぶ。予定画面に製品、対象版、環境、登録ケース名、受入条件、次の実行回を一覧表示する。「第 N 回を開始」で初めて実行を受け付ける。開始後は同じ画面で実行中と処理結果を読む。完了後はケース別の結果と今回の操作ログ、製品概要へ移動できる。スイートを選び直すと再実行できる。

| 状態 | 動作 |
| --- | --- |
| 開始前 | サーバーが登録時の予定を表示し、開始したい回の番号を受け取る。 |
| 実行中 | 同じ回の開始要求を再送しても、その回を返す。別の実行要求との競合は画面に表示する。ページ再読み込みで実行は開始されない。 |
| 完了 | ケース索引の合否・未報告と分母を表示する。不合格も「実行が完了した回」として保存する。 |
| 中断・処理エラー | 発行できた結果と、実行または発行が止まった状態を区別して表示する。次回に同じ番号を再利用しない。 |

## 入力・実行・公開

### 結果画面の読み順（FE-09）

1. 概要の先頭に、各スイートの最新索引の不合格件数と、同じ回に結び付いた業務判断依頼の件数を並べる。ゼロも明記する。予定数・判定済み数・未報告などの内訳を文字で添える。過去の依頼は別の件数と対象回で参照できる。判断待ちはこの画面で照合できた依頼を数え、回答を記録しない過去の依頼の解決状況を推定しない。新しい回の索引が未発行なら、表示している集計範囲を明示する。
2. 完了かつ予定が1件以上で、全予定ケースがその回の索引で合格した場合に限り、「第N回　X件すべて合格」を主見出しにする。スイート名を併記し、ログと再実行は補助操作にする。完了メッセージは自動テストの確認に限定する。中断、未報告混在、予定ゼロは全件合格に含めない。
3. 不合格詳細は今回の操作記録とレビュー済みの手順・期待値を突き合わせる。操作に結び付いた照合はその操作、最後に行う照合は完了した最後の操作を表示する。見出しで操作と未達条件を続けて読めるようにし、赤は未達条件に使う。観測値の欠落をボタンの不存在と断定しない。条件または操作を一意に特定できないときは分かる範囲を明記する。
4. 合格1・不合格1・過去の判断依頼1件の保存記録で入口を確認する。判断待ちがある最新回、未報告混在、判定済みゼロと合格のみの回を照合し、1440×900 と390×844の初期表示で主見出し、移動先、証跡の回を確認する。

### FE-09 の画面構成

- 概要の見出しはテスト対象の製品名とし、画面操作を自動で検証するサービスの役割を一文で添える。不合格件数と人の判断待ち件数は同時に読める。依頼がある回は、問いからその回の証跡へ移れる。ゼロ件の依頼に専用の空欄を設けない。
- 自動テストの結果にはスイート名・実行回を添え、不合格はその回の完了操作と確認できなかった条件、合格はレビュー済みの受入条件を表示する。操作や未達条件の根拠がない場合はケース名と記録の状態を使う。合格は先頭の1ケースを見せ、残りを展開できる。試験の目的から合否を書き換えない。
- 最新の集計で予定が1件以上あり、全件合格かつ今回の判断依頼がゼロなら確認完了を明示する。後続の実行中や索引未発行、未報告、予定ゼロでは完了を出さない。過去の依頼は履歴で開く。
- 全件合格はスイートの回と結論を一つの完了票に組む。補助操作はその下に置く。完了と受付番号を一つの面で示す構成は [GOV.UK の確認パネル](https://design-system.service.gov.uk/components/panel/) を参考にした。
- 不合格は白地に未達条件を朱色で示し、同回の操作を時刻付きの線で結ぶ。横幅があるときは判定の横、狭幅では直下にログを置く。選択と時刻の対応は [Playwright Trace Viewer の操作一覧](https://playwright.dev/docs/trace-viewer#actions) を参考にした。

### 集計・試験目的・判断依頼の読み分け

1. 判定済み数が予定数を下回る場合、先頭の集計に「判定済み X／N件」を出し、未報告があれば件数を並べる。X がゼロなら合格率を算出できない旨を添える。不合格件数と判断待ち件数はその下に残す。集計対象が過去の索引なら対象回の注記を維持する。
2. 全ケース合格のスイートと不合格を含むスイートが並ぶ場合、前者の合格ケース1件を先に短く示す。後者は登録ケース名を大きく示し、その下で実行した操作と未達条件を読む。どちらにもスイート名・回を添える。集計とケースの合否は索引どおりとする。
3. 判断依頼には同一ケース・同一回の自動判定と登録された問いを並べる。合格したケースで、照合項目が画面全体の名前付きボタンの表示1件なら、ボタン名と照合範囲を示す。ほかの条件では、確定したケース判定だけを示す。概要に同じ合格を重ねて表示しない。詳細には受入条件と依頼理由の記載状況を添え、指定された操作時刻を開く。
4. 保存済みの未報告、製品受入と不一致検出の混在、同一ケースの合格と判断待ちの3状態をPC幅・スマホ幅で再現する。件数や問いを読むための展開は不要とする。

### 詳細を開いた後の表示

1. 未報告の判定詳細では、未報告の結論の直下に「今回確認できなかった条件」を置き、その回の登録条件を原文順に列挙する。条件が空なら欄を省く。
2. 概要の合格ケースには「合格したケース」と明記し、登録名をかぎ括弧に入れた静的な見出しで示す。全件合格で判断待ちのない回は完了メッセージを先に読める。
3. 業務判断の詳細は、初めから依頼対象の操作を選択する。「判断対象の場面に戻る」は別の操作を選択している間だけログの下に出し、押すと対象行に選択とフォーカスを戻す。動画を開いている場合は再生位置も合わせる。動画の選択は操作ログに続く動画欄の先頭で行う。390×844 の保存済み依頼では、初期表示内にログと動画の選択ボタンが収まる。

### 概要・実行結果・証跡の往復

- 同一スイート内で各依頼の実行回を最新の索引と比較し、依頼詳細に埋め込む。過去の依頼は見出しの直上に「過去の判断依頼」と実行回を表示する。登録された問い、当時の合否・動画・操作ログを保ち、回答済みかどうかは推定しない。単独生成で比較する索引がない場合は「業務判断の依頼」とする。
- 履歴の各ケース行は登録名、ケースの合否、リリース判定を順に示す。判定へのリンクと操作ログへのリンクには個別の名前を付ける。ローカルの発行済み判定はその範囲を表示する。実行結果も「リリース判定」の表記を使う。
- 概要から開いた記録には移動元の行への参照を持たせる。判定から操作の流れ・動画へ進んでも引き継ぐ。概要に戻ると該当欄を展開し、元のリンクへフォーカスを戻す。参照のない直リンクは概要の先頭へ戻る。
- 実行結果から開いた操作ログには、そのスイート・実行回の結果に戻る導線を用意する。結果のケース欄が折り畳まれているときは展開し、元のケースに戻る。
- 予定数ゼロでは集計の先頭に「予定ケース 0件」を出す。不合格・判断待ちがともにゼロでも確認完了は出さない。
- 全回が同じID・同じ登録名の単一ケースなら、スイートの履歴冒頭にケース名を一度示す。ケースの追加・改名・入れ替えがあった系列は各回の名前を示す。集計値と操作ログへの参照は実行回ごとに表示する。
- 1440×900、390×844で現在／過去の依頼、空／合格／未報告の集計、ローカルの判定、履歴と実行結果からの往復を確認する。キーボードと動きを減らす設定でも、復帰先の行を読めること。

### 操作記録を読む構成

概要は対象と今回の件数を上段に置き、結果と判定履歴を広幅では左右、狭幅では上下に組む。未達条件の直前にある操作は、同じ回の照合済みの操作記録から、判定に結び付く操作までの末尾2件を元の順序で抜粋する。時刻は録画開始からの秒数。等間隔の印は順番を表す。ケース詳細を開くと抜粋の末尾と同じ操作を選択する。確認できる操作がないときは抜粋を作らず、操作行も選ばない。過去の合格を未報告の回に表示しない。

実行予定では選んだスイートと受入条件、ケース詳細では選んだ操作と記録時刻を強調する。履歴の開閉と操作行の選択は状態と同時に反映し、補助的な動きは短い一回に限る。動きを減らす設定では印と文字で状態を表す。

情報の選別に [Anything Frontend Product Design](https://github.com/RNA4219/anything-frontend-product-design)、判定と証跡の文字の強弱に [Art Direction](https://github.com/RNA4219/anything-frontend-art-direction)、選択と開閉に [Motion Atlas](https://github.com/RNA4219/motion-atlas) を参照した。装飾と重複する文言の点検には Damir Sokolovsky の [unslop](https://github.com/heydamir/unslop)（CC BY 4.0）を使った。

### 実行の受付と公開

全画面で同じ Lakda ロゴ、和文書体、本文の左右位置、フォーカス表示を使う。実行予定ではスイート選択と内容を隣に置き、狭幅では選択を先に置く。開始操作は紺、選択中の行は文字に加えて線や淡い面で示す。実行中は開始前と区別できる文言を出す。判定履歴では現在のタブと記録選択を引き続き使え、スイート結果とケース証跡は単体 HTML でも同じ共通スタイルを使う。

1. ローカル設定に製品概要の参照一覧、対象製品の配信ファイルと版の照合記録、各スイートの系列 ID・チェックアウト・エクスポート、録画ツールを登録する。登録時の予定と元のケース索引を照合する。ブラウザーからはスイート ID と実行回のみを受け取り、同じ画面からの要求を処理する。
2. サーバーは対象版に結び付いた配信ファイルのハッシュを確認し、承認済みエクスポートのローカル URL で製品を配信する。開始時に対象チェックアウトの Git 版と予定表を再照合する。ケースは既存のプラットフォーム用 replay で順に実行する。
3. 最初の追加実行は保存済みの最終回の次の番号とする。各回は専用ディレクトリを新規確保し、予定、今回の run、索引を保存する。集計には今回照合できた run のみを渡す。応答のなかったケースは未報告とする。合格率は合格件数を判定済み件数で割り、分母ゼロは「算出できない」と表示する。
4. 完了した回を既存の参照一覧に加えて製品概要を生成する。新しい概要は生成成功後に表示する。操作ログはケースと run を照合してから表示する。QEG の出力が発行されていない回は「判定未発行」と表示する。

## 受入試験

ケース画面の見出しにはスイートの実行回を使う。個々の replay に含まれる試行番号はケースの証跡に保持する。ローカルコンソールが配信する画面は、利用者が選んだ動画をブラウザー内で照合し再生する。元動画を HTTP で配信せず、照合に失敗したときは再生面を閉じて今回の操作ログを残す。

PC とスマホ幅で実画面の受入スイートを開始し、不一致を検出するスイートも実行する。開始要求の再送、再読み込み、再実行、サーバー再起動後の履歴を確認する。過去に合格したスイートで今回の報告が欠けたとき、最新の索引と概要が未報告になり、今回の画面から過去の証跡を開かないことを確認する。

## 起動と保存

`npm run platform` は同梱の配送案内サンプルをローカルで開く。製品には `npm run platform -- --init <設定.json>` でひな形を作成し、`npm run platform -- --config <設定.json>` で起動する。既定の画面ポートは 18872。製品は登録済みの `baseUrl` で別に配信する。[導入手順と設定例](../../../examples/e2e-platform/README.md)

初回はスイートの `id`、`name`、`checkout`、その配下の `scenarios`、対応する `featureSpec` と `manualCaseSet` から予定を作る。登録時に仕様とケース集のハッシュをエクスポート時の版と照合する。実行履歴が空なら開始前の画面を開き、第1回を予約した時点から実行回を保存する。既存の履歴を引き継ぐ設定では `sources` の記録からスイート名と最新回を復元する。

`target.directory` に配信ファイル、`target.observation` と `target.binding` に対象版を照合する記録を指定する。`store` に実行回と表示用 HTML を保存する。初回の録画用ツールは PATH から検出し、設定に `ffmpeg`、`ffprobe` の絶対パスがあればそちらを使用する。

各実行回には照合済みのケースごとに受領記録を保存する。中断後はこの記録と manifest が一致した run を回収する。開始前に CLI が要求を拒否して run を返さなかった場合は未報告となる。開始後に録画が失敗し Lakda がエラーを報告した場合は実行エラーとして集計する。いずれも過去の動画へのリンクは付けない。

ケース名と受入条件を同じ行に置き、選択と開始を別の操作にした。ケースを選びながら予定を読み、今回開始するスイートをボタンの直前で確かめられる。[参照したタスクリストの実画面](https://design-system.service.gov.uk/components/task-list/default/)
