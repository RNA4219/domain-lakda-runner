# 製品の構成とドメインテストの対応

対象は要件 DOM-01〜04。製品担当者が対象版の業務と保証すべき振る舞いを決め、ケース設計者がそれを確かめる確認項目を登録する。製品概要のケース合格率と独立した読み取り専用の集計である。

## 入力と操作

`lakda coverage map --config map.json [--input 今回の結果.json] [--runs-dir runs] [--format json|html] [--out 新規ファイル]`。既定は標準出力への JSON。HTML はブラウザーで開ける。実行結果を省くと設計時点のマップになる。正常な集計は不合格や未設計が残っても終了 0。壊れた参照、異版の入力、不整合な証跡は診断を出して失敗する。既存の出力は保持する。

1. 製品構成を `aym.architecture/v1` の JSON で用意する。`nodes` の ID と `connections` の接続元・接続先・ラベルで要素と連携を区別する。同方向でも意味の違う接続を別々に参照できる。接続の出典も保持する。[参考実装](https://github.com/RNA4219/ai-yori-murasaki/blob/0889033a2667d497394aae603e2614f9c37a4bf1/ai_yori_murasaki/web/architecture/model.mjs)
2. `lakda/domain-map/v1` の `architecture` から構成ファイルを相対指定し、`product` と `version` を固定する。`behaviors` に ID、業務名、振る舞い、出典、受入条件、対象要素・連携を登録する。対象外は `excluded` に理由を残す。構成要素や接続に振る舞いが一つもなければ「振る舞い未登録」と表示する。
3. `cases` は有効なケースの ID・版と `checks` を持つ。各確認項目にはケース内で一意な ID と、保証する振る舞いの ID を指定する。対応のないケースも登録できる。登録順を出力に保つ。[記入例](../../../examples/domain-coverage/misskey/map.json)
4. 今回の証跡を指定する。汎用の `lakda/domain-run/v1` は `product, version, runId, cases` を持ち、ケースの `id, revision, checks`、確認項目の `id, result`（passed / failed / partial）を記録する。報告には元の実行 ID、証跡ファイルの SHA-256、該当項目の位置を残す。実行ごとに一つの結果ファイルを選ぶ。
5. Misskey のような単一ケースの操作記録は `product, version, caseId, caseRevision, startedAt, steps` から取り込める。マップの `step.action` と一致する観測だけを使い、`step.equals` の全項目を照合する。観測なし、必要な値の欠落は未判定。観測値の不一致は不合格。ケース全体の合否を各操作に転記しない。
6. Lakda の `lakda/e2e-case-index/v1` には `--runs-dir` を併用する。ローカルまたは CI の系列・実行回、製品コミット、対象環境、ケース版、受入条件、レビュー済み判定条件、manifest と証跡を照合する。マップは `environment` とケースの `obligations` を指定し、各確認項目の `obligation` は 1 始まり。個別判定のログを優先する。個別ログがない履歴では、唯一の判定条件について正常完了または明示的な期待値不一致が確定した場合だけ結果を採用する。

## 被覆の読み方

### ローカルコンソール

製品概要の「検証範囲」から登録スイートの最新回を開く。実行結果の「この回の検証範囲」はその回を固定する。URL は `/coverage?suite=<id>&attempt=<回>`。最初の実行前は設計だけを表示する。各スイートの `coverageMap` はコンソール設定からの相対パスで、`product` は登録製品 ID または登録表示名、版と環境は登録値に一致すること。集計の分母はそのマップの対象内の振る舞いである。

最初にスイート・回、判定済みの分子と分母、残った振る舞いの名前と理由を表示する。確認済みの詳細、出典と内部 ID は必要なときに開く。構成図から詳細へ移ると選択項目にフォーカスを移す。概要への戻り口を保持する。狭幅では本文を一列にし、色と動きに依存せず状態を読めること。

最新回は実行予約時点で切り替える。新しい回の索引が未発行なら以前の回を採用しない。明示した履歴が存在しなければ 404。設定がないときは「検証範囲は未登録」、証跡の照合に失敗した場合は「証跡を照合できません」と示す。見本の実行は設計を参照するために使い、製品実行の被覆に加えない。

HTML の「システム構成図」で箱または接続線を選ぶと、その対象の「保証する振る舞い」から受入条件と今回の証跡を開ける。同じ向きの線に複数の接続がある場合は、それぞれの理由と根拠を表示する。ファイルを別の PC で開く場合も図は単体で動作する。参照した実行記録へのリンクを使う場合は、元の記録も同じ相対位置に置く。

「構成ファイルを開く」から別の構成図、CloudFormation、複数の `package.json` をタブ内で確認できる。元の振る舞いと照合するには「読み込めるファイルと見本」の「対象製品の構成図を開く」で戻る。図の表示上限は要素100件、接続300件、指摘300件。上限を超える製品でも検証結果の表を読める。

Misskey の記入例を試すには、リポジトリのルートで次を実行する。実証跡はローカルに保存したものを指定する。

```powershell
npm run build
node dist/cli.js coverage map --config examples/domain-coverage/misskey/map.json --format html --out design.html
node dist/cli.js coverage map --config examples/domain-coverage/misskey/map.json --input result.json --format html --out coverage.html
```

分母は対象内の振る舞い数。複数の要素・連携やケースに対応しても一度だけ数える。設計済みは一つ以上のケースで対応する確認項目が登録されている数。各ケース内ではその振る舞いに必要な確認項目すべての合格を要する。代替ケースが一つ完了すれば合格を確認でき、いずれかに明示的な不合格があれば不合格を優先する。未到達・未報告・旧ケース版には今回の判定を付けない。対象外は別に表示し、分母 0 の比率は JSON の null とする。

## 操作の流れと読みやすさ

構成図の「操作の流れ」では、見たい操作を選び、画面から保存先まで順にたどれる。各工程には役割、担当リポジトリ、対応する振る舞いの今回の判定と確認項目へのリンクを表示する。工程のない既存の構成も読み込める。

`aym.architecture/v1` には次の項目を任意で指定できる。

| 指定箇所 | 意味 |
| --- | --- |
| `nodes[].role` | 「画面」「API」「キュー」「承認担当」など、表示・検索・グループ分けに使う自由な役割名。省略時は基本の種類を表示する。 |
| `nodes[].repository` | 担当する `kind: repository` の要素 ID。担当の分からない工程は「未登録」と表示する。 |
| `flows[]` | 一意の `id`、操作の表示名 `name`、順序付きの `steps`。最大100操作、各1〜100工程。工程の `node` は構成要素の ID。 |
| `steps[].via` | 直前の要素から現在の要素への接続名。指定時は向きと名前が一致する接続が一つ必要。省略すると操作順だけを表す。 |
| `connections[].observe` | `screen-api` を指定した接続は同じ向きに一件だけ、公開済みの画面 ID と API ID の組に対応させられる。 |

例えば注文入力から受付APIを呼ぶ操作は `{"id":"order","name":"注文登録","steps":[{"node":"entry"},{"node":"gateway","via":"注文を送信"}]}` と書く。画面の「操作・役割・工程を追加」から既存または新規の要素で操作を作り、「編集した構成 JSON を保存」で再利用できる。別ファイルや編集したコピーの表示中は、その構成単体の情報を使う。

通信観測を重ねる場合は、計測に使った画面・APIカタログと実行索引を指定する。

```powershell
lakda coverage map --config map.json --surface-catalog catalog.json --input index.json --runs-dir runs --format html --out measured.html
```

`lakda/e2e-case-index/v1` と SDK の `lakda/surface-run-index/v1` に対応する。対象製品・版・環境、実行索引と manifest、計測定義を照合する。マップに登録されたケースは版も照合する。「観測あり」は該当する通信を記録したことを示し、証跡からレーン、ケース結果、実行回を確認できる。「観測なし」は該当する定義で完全な計測がある場合に限る。設計だけの接続や計測不足は「未計測」。確認項目の判定はその項目の証跡から求める。コンソールの公開範囲を限定した画面・APIレポートには従来の公開設定が適用される。

## 受入条件

- 100要素・100工程でも、幅320pxと1280pxの初期表示は100%。表示中の工程ボタンは最大5件。工程番号の選択や名前・役割の検索で末尾へ直接移動できる。「全体を表示」から工程を選ぶと100%で対象を読める。
- 構成図と詳細は広い画面でも一列に並ぶ。6工程以上では工程一覧を折りたたんで開き、必要なときだけ前後の工程を縦に表示する。「この工程を図で見る」から選択した箱へ、箱や線から詳細へ、「図に戻る」で元の対象へキーボードでも戻れる。長い本文は1行あたり全角約46文字を上限とする。
- 新しい操作、任意の役割と担当、名前付きの接続を追加した後に構成を保存して開き直すと、操作順・接続・役割・担当が復元される。
- 画面からAPIへの通信を記録した合成ケースでは、ケース全体が失敗しても通信は「観測あり」。確認項目の証跡がなければ振る舞いは「今回未判定」。旧ケース版や別の図に当該証跡を表示しない。

- 登録・解除・二重登録の三項目で最初の二つだけを設計・確認すると、設計も今回判定済みも 2/3。空の再実行では設計 2/3、今回判定済み 0/3。
- 登録が成功しても一覧に反映されなければ登録は不合格。解除まで到達しなければ解除は未判定。
- 逆向き接続、存在しない振る舞い、重複する ID、異版、取り違えた manifest を検出する。対象外だけの地図、未割当ケース、観測の欠落も表示できる。
